## 1. The measurement

### 1.1 What was asked

*How often does the live board actually carry leftover uncommitted ticket writes?* A monitor for a
condition that never occurs is a different proposal from one for a weekly occurrence.

### 1.2 Method

Read-only throughout. Only `git rev-parse`, `git log`, `git show`, `git status`, `git cat-file
--batch` and `git diff --quiet` were run against `blaze-pm`. No `blaze` verb was invoked against the
board at all, no file in it was written, and nothing was committed or pushed. Scripts used are
throwaway and live in the session scratchpad, not in either repo.

Three independent evidence sources were tried. Two answer; one is invalid and is reported as such.

### 1.3 Observation window

Board `blaze-pm`, branch `BLZ-305-v4-spine`, at `70197405`:

- **345 commits**, spanning **2026-07-15T23:53:32+10:00 → 2026-08-29T14:05:23+10:00** — a **45-day**
  window. 230 of those commits touch `projects/`.
- Board is `"commitMode": "batch"` (`blaze.config.json` at that ref). This is load-bearing: see §1.7.
- 189 commits on the branch are not on `origin/main`. (The kickoff brief says 32; that figure is
  stale at this ref. The discrepancy is not material to this ticket, but it is recorded rather than
  quietly reconciled, and is listed in §8.)

### 1.4 Figure 1 — direct state of the tree: **zero**

At `blaze-pm` `70197405`, `git status --short` over the whole board returns **0 lines**. There are
**zero** uncommitted ticket writes on the live board.

**What this can and cannot establish.** This is *one sample*, and it is taken at the least
informative possible moment: the immediately preceding commit is `70197405 blaze: 2026-08-29 board
update (9 moved)`, a flush at 14:05:23, and the current session's own queue file
(`.blaze/pending/auto-e2eb4d4f-….jsonl`) was created empty at 14:05. The coordinator flushed the
board and handed off. A clean tree ten seconds after a flush is close to no evidence about a rate.
It is reported because it is a true, pinned observation, **not** because it supports "the condition
never happens".

carrying **185 queued board ops** in total:

By op: **107 `move`, 39 `log`, 35 `new`, 4 `edit`.** Queued between

**Every one of them is stale, not pending.** The tree is clean (§1.4), so every file these entries

**What filed them.** For each entry I took the destination path (the last element of its `files`

**Of the 118 that can be traced, the flush path filed 0 and a human filed all 118.**

Gap between consecutive board commits (n=344): p50 **0.36 h**, p75 1.26 h, p90 **8.16 h**, p99 36.2
h, max 119.9 h. That p90 is the honest upper bound on how long *any* write can sit uncommitted on
this board before something commits it.

### 1.7 The mechanism, established

The three figures compose into one explanation, and it is not the one the ticket assumes.

1. On a `commitMode: "batch"` board, every board-mutating verb **writes the ticket file immediately**
   and **queues the commit intent**. `commitOrQueue` returns `{ queued: true }` and touches git not
   at all (`scripts/commit-or-queue.mjs:31-56`). Reconcile is routed through the same door
   (`scripts/reconcile.mjs:2103-2116`, BLZ-404).
2. Therefore **the ticket tree is uncommitted by design between every verb and the next `blaze
   commit`**. On this board the condition "`projects/` carries uncommitted ticket writes" is not
   rare — it is the normal state for part of every working session. That is state (b).
3. `blaze commit` drains **only the caller's own session queue**, keyed by `BLAZE_SESSION` or an
   `auto-<harness-session-id>` fallback (`scripts/pending-ledger.mjs:16-23`,
   `scripts/commit-runner.mjs:76-80`). A new agent session gets a **new** id and therefore a **new,
   empty** queue. The previous session's queue is invisible to it unless `--all` is passed.
4. So an abandoned session's queue is never drained, while the operator — needing the board filed —
   commits the files **by hand** with a bespoke message. The write lands; the ledger entry orphans.
   That is precisely the 118/0 split in §1.5 and the 66.4% in §1.6.
5. `commit-runner.mjs:88-100` already detects and signposts exactly this ("*nothing to flush for
   session X — N op(s) queued in other sessions (…); use `--all` to sweep them*") — but only for
   someone who runs `blaze commit` in a session that has nothing of its own to flush. Nobody did.

### 1.8 An invalid measurement, reported rather than suppressed

I also tried a fourth source and it does **not** work. For every commit touching `projects/`, I read
the committed blob's `updated:` frontmatter and compared it against the commit's own date, on the
theory that a write filed days after its stamp is the footprint of a write that sat uncommitted.

It produced **3059 of 4019 ticket-file writes (76.11%) filed ≥1 day after their stamp**, and
**968 of 1188 (81.48%)** when restricted to content modifications with rename detection on.

**Both figures are wrong and I do not believe them.** `updated:` is not restamped on every write.
`scripts/reconcile.mjs:1990` reads:

```js
if (d.moved) { fm.updated = today; dirty = true; }
```

Reconcile stamps `updated` **only when the ticket moved**. Its non-move writes — backfilling a
`resolution`, recording `branch`/`pr` — leave `updated` alone. Verified directly on `blaze-pm`
`fdb1375e` ("*blaze: 2026-08-28 board update (1 logged, 56 reconciled)*"): 56 tickets each gained
`+branch:`/`+pr:` lines with **no** change to `updated:`, e.g. `BLZ-107` still reading `updated:
2026-08-23` inside a commit dated 2026-08-28. `git mv`-style relocations carry the field forward
unchanged too.

The 76%/81% figures are an artifact of that, plus the 2026-08-15 `rescue:` bulk import. **They are
recorded here so nobody re-derives them and believes them, and they are used for nothing.**

### 1.9 What the evidence establishes, and what it cannot

**Establishes:**

- The condition BLZ-432 names — a *leftover, never-filed* ticket write — has **zero** instances at
  `blaze-pm` `70197405`, and over the traceable 118-op sample **no write survived more than 5.65
  hours** before something committed it.
- A different condition **does** occur, at scale and durably: **185 orphaned pending-ledger ops in 8
  abandoned session queues, aged 2–5 days**, none of which any surface reports unless someone
  happens to run `blaze commit` from a session with an empty queue of its own.
- The `blaze commit` flush path authored **0** of the commits that filed those 185 ops, and **33.6%**
  of board commits overall. The dominant filing mechanism on this board is a human typing `git
  commit`.

**Cannot establish:**

- **A rate for "the tree is dirty right now".** Git records commits, not working-tree dirtiness
  between them. §1.4 is a single sample taken seconds after a flush. The only defensible bound is
  the inter-commit gap (§1.6): p90 8.16 h.
- **Whether a state-(a) failed commit ever happened in this window.** A failed `commitFile` leaves
  *no durable trace* — in `per-op` mode no ledger entry is ever written, and in `batch` mode a
  failed flush keeps a queue that is byte-identical to a healthy queued one (`commit-runner.mjs`'s
  `bail()` leaves the ledger untouched by design). It is reported loudly on stderr at exit 1 **at the
  time**, and then it is gone. History cannot answer this question, and I am not going to produce a
  number for it.
- **Anything about a `per-op` board.** Every figure here is from a `batch` board. A `per-op` board
  has no ledger, and the whole discriminator in §2 is unavailable on it. Stated in the ADR.

## 2. The three states, precisely

Take a ticket file `F` under `projects/<KEY>/` whose working-tree content differs from `HEAD`.

| | State | Definition | Decidable? | By what |
|---|---|---|---|---|
| **(a)** | **Failed prior commit** | A blaze verb wrote `F` and its commit did not land — advisory lock held, pre-commit hook refused, detached HEAD. | **No** (see below) | — |
| **(b)** | **Batch-queued by design** | A blaze verb wrote `F` on a `commitMode: "batch"` board and queued the intent. Healthy; the normal steady state. | **Yes** | a pending-ledger entry naming `F` |
| **(c)** | **A human's in-flight file** | A person edited or created `F` by hand — a draft, a `NOTES.md`, a swapfile. Healthy; none of blaze's business. | **Yes, negatively** | *no* ledger entry names `F` |

### 2.1 (b) is decidable, cheaply, and without either forbidden mechanism

An entry in any `.blaze/pending/*.jsonl` records `files` as **repo-relative paths written by blaze
itself** (`scripts/commit-or-queue.mjs:47` — `files: unique.map((f) => relative(root, f))`). So the
question "is `F` queued?" is a lookup in a JSONL file blaze authored, not an interpretation of git's
output. Deciding whether that queued write is still outstanding is one exit code per recorded path:

```sh
git -C <root> diff --quiet HEAD -- "<path recorded in the ledger>"   # 0 = matches HEAD, 1 = differs
```

**Validated empirically** (throwaway repo, this session), against both defects that killed the
earlier designs:

| Probe | Symlinked `projects/` + dirty file | Path with a space and non-ASCII (`ZZZ-1 spaced ünicode.md`) |
|---|---|---|
| design 2's `git status --porcelain -- projects/` | **empty output, exit 0 — under-fires**, exactly as the round-4 review found | n/a |
| `git diff --quiet HEAD -- <recorded path>` | **exit 1 — fires correctly** | **exit 1 — fires correctly** |
| same probe, untracked `NOTES.md` (state c) | exit 0 — correctly invisible | — |

The symlink defect does not apply because the probe is driven by the **ledger's recorded paths**,
never by a filesystem walk of `projects/` or a pathspec through the symlinked directory. The quoting
defect does not apply because **no path is ever parsed out of git's output**; the path goes *in*,
after `--`, and only an exit code comes *out*.

### 2.2 (a) and (c) cannot be told apart, and that is the finding

For a dirty `F` with **no** ledger entry, blaze holds no evidence at all that distinguishes
"a verb wrote this and the commit failed" from "a person wrote this":

- On a `per-op` board there is no ledger, so (a) writes nothing anywhere.
- On a `batch` board a *failed flush* deliberately **keeps** the queue, so state (a)-after-a-flush is
  byte-identical to state (b).

The only way to make (a) decidable later is to make a failed commit leave a durable record — a new
persistent artifact, a new failure mode when *it* cannot be written, and a new thing to garbage-
collect. **That is refused here** (§3.4), because state (a) is already reported at full volume by
the pass that causes it, at the moment it happens — **surfaced at the invoking surface, which is not
always a process exit**:

| Invoking surface | How a failed commit surfaces | Pinned by |
|---|---|---|
| the CLI (`blaze reconcile --apply`) | `FAILED TO COMMIT` on stderr, **exit non-zero** | `tests/reconcile-commit-routing.test.mjs:247-258` |
| the supervisor loop (`blaze start`) | **an error/warning event published to the feed** — there is no process exit at all | `tests/reconcile-commit-routing.test.mjs:163` |

> `reconcile: FAILED TO COMMIT — the advisory commit lock is held by another writer. N ticket(s)
> moved — already written to disk and now UNCOMMITTED (a dirty tree), not merely un-applied. Re-run
> once the lock clears, or commit the tree manually.`
> — `scripts/reconcile-commit-report.mjs:106-109`, and its sibling for a non-lock failure at `:115-120`

Saying "state (a) exits 1" would be an over-claim of exactly the kind ADR-0030 forbids: it is true of
one surface and false of the other. The correct statement is **surfaced at the invoking surface —
exit 1 for the CLI, an error event for the loop**.

**And on a `batch` board the failure point moves.** Reconcile does not commit there at all; it
queues. A commit failure therefore surfaces from `blaze commit` at *flush* time, not from reconcile
at *pass* time — which is a further reason the detector does not belong in reconcile.

Nothing about state (a) is silent on any surface. What is missing is only a *reminder on a later
pass*, and §3 argues that reminder is not worth its cost.

**BLZ-128, the one finding that could have overturned this, is settled.** It alleged a silent
failed-commit route (a stale old-path pathspec in `git add`). Verified independently against
`1b00f3a` with live fixtures and closed `cannot-reproduce`:

- The pre-rename `touched.push(t.file)` at `reconcile.mjs:2018` is **load-bearing, not stale**. With
  no `git add -A` anywhere — deliberate, `serve-commit.mjs:2-3` — naming the old path is the only way
  to stage the **deletion side of the rename**. `git add <old> <new>` on a tracked ticket exits 0 and
  stages `R defined/T-1.md -> done/T-1.md`. BLZ-128's own AC-2 would have broken the rename.
- The whole-pathspec rejection is reachable only for a ticket whose old path was **never committed**,
  and even then it fails loudly: `commitFile` returns at the add step and `git commit` never runs.
- The silence is closed and already pinned at `tests/reconcile-commit-routing.test.mjs:247-258`.

The premise of §2.2 therefore holds.

**So: (b) is decidable. (c) is decidable as "not (b)". (a) is not decidable after the fact, and the
design says so rather than implying it is covered.** This is a stricter reading than design 2's —
design 2 claimed to separate three states and actually separated none.

## 3. Recommendation

### 3.1 The decision

**Reconcile does not detect a cross-pass uncommitted ticket tree. Round 5 stands — and it now stands
on a measurement rather than on an argument.**

**And the discriminator that round 5 correctly named — the pending ledger — is real, already exists,
and belongs to `blaze commit`, not to reconcile. Phase 2 surfaces it there, read-only.**

The round-5 rationale already living in the tree said the right thing without being able to prove it:

> "*There is no version of this that works from the tree alone — telling those apart needs the
> pending ledger, not `git status`*" — `scripts/reconcile.mjs:2313-2325`
> "*That is a real feature with its own ticket and its own design — it is not built here.*"
> — `tests/reconcile-unfinished-pass.test.mjs:22-24`

§1 supplies the evidence. §2.1 supplies the mechanism. Neither existed when round 5 was written.

### 3.2 Why reconcile is the wrong owner, on the evidence

A cross-pass detector inside reconcile would, over the measured 45-day window:

- have fired **zero** times on the condition it exists to catch (§1.4, §1.5 — no write survived 5.65
  hours, none is outstanding now); and
- have fired **on essentially every applied pass** on state (b), because on a `batch` board every
  applied pass leaves the tree dirty by design until the next flush (§1.7).

That is a signal-to-noise ratio of 0. It is also, precisely, design 2's failure re-derived from
data instead of from a review. **A monitor whose measured true-positive count is zero and whose
measured false-positive rate is ~100% should not be built**, and BLZ-353's rule ("measure before any
severity or behaviour change") is what says so.

Reconcile is additionally the wrong owner on ownership grounds: it does not own the queue, does not
know whether one exists, and derives its answer from git rather than from anything a session wants
(ADR-0023 §3). The queue's owner is `blaze commit`.

### 3.3 What the operator does instead

Stated so the ticket carries it, per the ticket's own AC-4:

1. **For state (b), the normal case:** run `blaze commit` (this session's ops) or `blaze commit
   --all` (every session's). The verb already tells you when your own queue is empty but others are
   not (`commit-runner.mjs:88-100`).
2. **To see the whole picture before deciding:** run **`blaze commit --status`** — the one new thing
   phase 2 ships. Read-only. It lists every queue, its op count, its age, and per queue how many of
   its recorded files still differ from HEAD (*outstanding*) versus already match it (*orphaned —
   filed by something else, safe to clear*). This is the surface that would have made the 185 stale
   ops in §1.5 visible on any day in the last five.
3. **For states (a) and (c):** `git status` and a human judgement, exactly as today. Blaze does not
   claim to tell these apart, and after phase 2 it says so in the one place it currently does not
   (§3.5).

### 3.4 Explicitly refused, so nobody re-proposes it

- **A durable failed-commit record** that would make state (a) decidable. Refused: state (a) is
  already reported with a full remedy at the moment it occurs, at whichever surface invoked the pass
  — exit 1 for the CLI, an error event for the supervisor loop, and from `blaze commit` at flush time
  on a `batch` board (§2.2) — and the record would add a persistent artifact, its own write-failure
  mode, and its own GC problem to catch a condition measured at zero.
- **Making `blaze commit --status` clear orphaned queues.** Refused for phase 2: a read-only verb
  that also deletes is not a read-only verb. Clearing is a separate decision on a separate ticket
  (§8), and `--all` already drains them safely today.

### 3.5 The one product sentence that must change

The docs are already honest and thorough — `docs/guide/commands.md:120-133` said outright, **as of
`1b00f3a`** (quoted here as the phase-1 state; the last clause is superseded, see below):

> "Reconcile does **not** auto-recover an uncommitted prior pass, and it does **not** detect one
> either. … Telling a genuinely failed prior commit apart from a `commitMode: "batch"` board that
> queued by design, or from a human's own uncommitted edit under `projects/`, needs the pending
> ledger, not `git status` — that is a separate, unbuilt feature."

**Superseded by this PR, and it had to be.** BLZ-499 builds that ledger read, so the words "a
separate, unbuilt feature" became false the moment `--status` landed — two lines above the page's
own link to it. Leaving them would have broken BLZ-432's own acceptance criterion that the product
stop implying otherwise. The sentence now names `blaze commit --status` as the built discriminator
for the queued-by-design state, and says plainly that the other two remain invisible to it.

No live product string claims the board is "in sync" — every surviving instance of that phrase in
`scripts/` is an *anti*-claim (`reconcile.mjs:2280`, `:2309`; `views/reconcile-summary.mjs:66`,
`:119`). BLZ-433 did its job.

**Exactly one residual over-claim survives, and it is in the help text:**

`/home/rnamwoh/Documents/Code/blaze-worktrees/lane-b/scripts/cli.mjs:32`

```js
  reconcile: { file: "reconcile.mjs", desc: "sync board status to git/PR state", mutates: true },
```

Rendered to the operator at `cli.mjs:62` (`blaze` with no args) and `cli.mjs:78` (`blaze reconcile
--help`) as:

```
usage: blaze reconcile — sync board status to git/PR state
```

"**sync board status**" is unqualified: it names *the board*, promises a two-way settled state, and
omits both that it is dry-run by default and that it only ever looks at delivery-workflow tickets
whose branch/PR state git can see. It is the last unqualified use of the verb BLZ-404 round 5
removed everywhere else, and **no test pins it** (`grep -rn "sync board status"` matches `cli.mjs:32`
only), so it is free to change.

Phase 2 changes it to a bounded description and **adds the test that pins it**, so it cannot drift
back. Secondary, same class, same hunk of work: `docs/guide/getting-started.md:166` ("*which syncs
board status from a linked code repo's branch/PR state*") and `docs/design.md:269`, which quotes
`"standalone board — nothing to reconcile"` — a string the product has not emitted since BLZ-433
(the live string is `reconcile: no projects configured — nothing to reconcile.`).

## 4. Why designs 1 and 2 stay rejected under this proposal

The risk in any BLZ-432 proposal is that it quietly becomes one of the designs already refuted. Point
by point:

### Against design 1 (the `dirtyTicketPaths` recovery sweep)

| Design 1 did | This proposal |
|---|---|
| **Wrote** — attempted the commit for whatever it found | **Reads only.** `blaze commit --status` stages nothing, commits nothing, and calls no mutating git command. |
| **Discovered** files from `git status --porcelain -- <projectsDir>` | **Discovers nothing.** It asks only about paths blaze itself recorded in its own ledger. It cannot name a file blaze did not write. |
| **Parsed paths out of porcelain output** (fixed-offset `slice(3)`; broke on ` D path`, spaces, C-quoted non-ASCII) | **Parses nothing.** Paths go *in* after `--`; an exit code comes *out*. Validated against a spaced, non-ASCII filename in §2.1. |
| **Swept a human's `NOTES.md` and another project's files** into a reconcile commit | Structurally impossible: an untracked `NOTES.md` has no ledger entry, so it is never asked about (validated, §2.1), and nothing is committed regardless. |
| **Half-committed staged renames**, leaving a duplicate ticket id in HEAD | No commit, no staging, no rename handling. |

The recovery half of design 1 is not narrowed here — it is **absent**. Nothing in this proposal ever
files anything.

### Against design 2 (the detect-and-report boolean)

| Design 2 did | This proposal |
|---|---|
| Conflated (a), (b) and (c) and **asserted the wrong one** | Separates (b) positively and (c) negatively, and **declares (a) undecidable in writing** (§2.2) instead of asserting it. |
| Blamed a healthy `batch` board for "a previous pass failed to commit" and **exited 1** | (b) is the *expected* reading, labelled "outstanding — run `blaze commit`". No exit code changes. Reconcile's exit codes are untouched. |
| **Wedged reconcile at exit 1** on a human's untracked file, printing a no-op remedy | Lives in `blaze commit`, not reconcile. Reconcile gains nothing and cannot be wedged. A human's file is invisible to it. |
| **Under-fired on a symlinked `projects/`** — the case it was written to close | Ledger-driven paths, not a pathspec through `projects/`. **Reproduced design 2's under-fire and this probe's correct fire, side by side, in §2.1.** |
| Lived in `reconcile()` and gated its CLI | Lives in `commit-runner.mjs`. `scripts/reconcile.mjs` is **not touched at all** in phase 2. |

The load-bearing difference is not that this boolean is better written. It is that **the question is
asked of a different oracle** — blaze's own record of what it wrote, instead of git's report of what
the tree looks like — and asked by the component that owns that record.

## 5. Blast radius, against BLZ-394 explicitly

BLZ-394's rule: *a session must not author a commit touching tickets it does not own*; `--apply`
commits **`touched`**, the exact list of files this pass wrote (`scripts/reconcile.mjs:2115`,
`files: touched`), never `git add -A`, never a discovered set. Its ACs add that a filtered run must
never be mistakable for a whole-board one.

**This proposal does not widen the commit's blast radius, because it does not commit.**

1. **`scripts/reconcile.mjs` is not modified in phase 2.** `touched` is unchanged, the
   `commitOrQueue` call at `:2103-2116` is unchanged, `--project`/`--ticket` scoping is unchanged.
   The set of files a reconcile commit can name is byte-for-byte what BLZ-394 left it as.
2. **The new verb has a blast radius of zero.** `blaze commit --status` runs `git diff --quiet HEAD
   -- <path>` (read) and reads `.blaze/pending/*.jsonl` (read). It calls no `git add`, no `git
   commit`, no `git mv`, no write of any kind. The verb stays `mutates: true` in `cli.mjs`; the
   entry carries `readOnlyFlags: ["--status"]`, exempting this one invocation from the BLZ-121
   gate — and phase 2 pins that with a test.
3. **`blaze commit`'s existing commit path is not modified.** The set of files a flush stages remains
   exactly `entries.flatMap(e => e.files)` filtered by existence/trackedness
   (`commit-runner.mjs:130-134`). `--status` returns before the lock, the `git add` and the `git
   commit` — the same position `checkBranch` occupies, and for the same reason.
4. **Cross-project reporting is not cross-project writing.** `--status` will report queues holding
   ops for projects the caller does not own — that is the point, since the 185 orphans in §1.5 span
   several. BLZ-394 governs what a session **writes**; naming a foreign queue in a read-only report
   is what BLZ-394 AC-5 *asks* for ("a filtered run must not be mistakable for an in-sync board").
   Phase 2 states the scope on every run, per that AC.

**BLZ-347 specifically:** no porcelain path parser is reintroduced. The only surviving `--porcelain`
call site in `scripts/` is `loops/groomer.mjs:409-418`, which returns whole lines for set-comparison
and is documented as never parsing paths. Phase 2 adds no `--porcelain` call and no `-z` parser.

**What the measurement changes.** The condition BLZ-432 names was measured at zero. A different

nothing. That is design 2's defect, re-derived from data rather than from a review.

## Decision

### 1. Reconcile does not detect a cross-pass uncommitted tree, and this is now a MEASURED decision

Round 5 stands. `reconcile()` gains no probe, no flag, no field and no exit code for this condition,
and `scripts/reconcile.mjs` is not modified. Reconcile knows one thing — whether THIS pass found a
code-bound change to make — and says exactly that.

What is new is the standing: this was an argument from a review, and it is now a decision with a
figure behind it. A monitor whose measured true-positive count over 45 days is zero, and whose
false-positive state is the board's normal steady state, is not built. BLZ-353's rule — measure
before any severity or behaviour change — is what settles it.

### 2. The oracle is the LEDGER, not the tree, and it belongs to `blaze commit`

Every rejected design asked git what the tree looks like. That question cannot be answered usefully:
a dirty ticket file looks identical whether a verb wrote it, a verb wrote it and failed to commit, or
a person wrote it.

The answerable question is a different one — *what did blaze record that it wrote?* — and blaze
already keeps that record. A pending-ledger entry stores repo-relative paths written by blaze itself
(`commit-or-queue.mjs`, `files: unique.map((f) => relative(root, f))`). Whether a recorded write is
still outstanding is one exit code per recorded path:

```sh
git -C <root> diff --quiet HEAD -- "<path recorded in the ledger>"
```

Paths go IN, after `--`; only an exit code comes OUT. Nothing parses a path out of git's output, so
BLZ-347's deleted parser is not reintroduced, and a filename with a space or a non-ASCII character
cannot wedge it. Nothing walks `projects/`, so a symlinked `projects/` cannot silence it — the case
design 2 was written to close and missed.

**The recorded path is not automatically the path git knows, and assuming it was cost this design a
review round.** `commitOrQueue` records `relative(root, f)` and nothing in `config.mjs` calls
`realpath`, so on a board whose `projects/` is a symlink the ledger holds the through-symlink
spelling while git's index holds the real one. `ls-files --error-unmatch` then never matches, and
EVERY op on such a board reports `outstanding` forever — including the already-filed ones this verb
exists to find. That is the OVER-fire twin of design 2's under-fire, on design 2's own fixture, and
it corrupts the verb's headline distinction. The implementation therefore resolves each recorded
path's longest existing prefix and re-relativises it against the real root before probing, and
reports under the recorded spelling, which is what the operator has on disk. Resolving a PREFIX
rather than the whole path is what keeps a move's already-deleted old path answerable.

Verified directly, end to end through the real `blaze new` runner on a symlinked batch board:

| probe | symlinked `projects/`, op already filed | symlinked, op genuinely unfiled | `ZZZ-1 spaced ünicode.md`, dirty |
|---|---|---|---|
| `git status --porcelain -- projects/` (design 2) | empty, exit 0 — **under-fires** | empty, exit 0 — **under-fires** | n/a |
| probing the RECORDED path verbatim | `outstanding` — **over-fires** | `outstanding` (right, by luck) | fires |
| probing the RESOLVED path (shipped) | **`settled`** | **`outstanding`** | **fires** |

The owner is `blaze commit`, which owns the queue. Reconcile does not own it, cannot see whether one
exists, and derives its answer from git rather than from anything a session wants (ADR-0023 §3).

### 3. TWO of the three states are decidable and the third is declared UNDECIDABLE rather than asserted

For a ticket file under `projects/` that differs from HEAD:

| State | Decidable | By what |
|---|---|---|
| (b) batch-queued by design | **yes** | a ledger entry names the file |
| (c) a human's own in-flight file | **yes, negatively** | no ledger entry names the file |
| (a) a genuinely failed prior commit | **NO** | nothing durable distinguishes it |

State (a) leaves no trace after the fact. On a `per-op` board no ledger entry is ever written; on a
`batch` board a failed flush KEEPS its queue by design, so it is byte-identical to a healthy queued
one. This is stated rather than papered over, because design 2's specific defect was claiming to
separate three states while separating none.

State (a) is not silent. It is reported at full volume by the pass that causes it — **at the invoking
surface, which is not always a process exit**: `FAILED TO COMMIT — … already written to disk and now
UNCOMMITTED (a dirty tree), not merely un-applied` on stderr with a non-zero exit for the CLI
(`tests/reconcile-commit-routing.test.mjs:247-258`), and a published error event for the supervisor
loop, which never exits at all (`:163`). On a `commitMode: "batch"` board the failure point moves
again: reconcile queues rather than commits, so a commit failure surfaces from `blaze commit` at
flush time, not from reconcile at pass time.

Saying simply "it exits 1" would be true of one surface and false of the other — the over-claim
ADR-0030 forbids — so this ADR does not say it.

BLZ-128 alleged a silent route to state (a) (a stale old-path pathspec in `git add`) and would have
overturned this reasoning had it held. It was verified independently against `1b00f3a` with live
fixtures and closed `cannot-reproduce`: the pre-rename `touched.push(t.file)` is load-bearing, not
stale — with no `git add -A` anywhere (deliberate; `serve-commit.mjs`), naming the old path is the
only way to stage the DELETION side of the rename, and BLZ-128's own AC-2 would have broken it. The
whole-pathspec rejection is reachable only for a ticket whose old path was never committed, and fails
loudly there.

What is missing is only a reminder on a later pass, and that is not worth a durable failure record
with its own write-failure mode and its own garbage to collect. Refused, in writing, so it is not
re-proposed.

### 4. The report is READ-ONLY, and the read-only-ness is pinned, not asserted

`blaze commit --status` reads the ledgers and runs `git diff --quiet`. It stages nothing, commits
nothing, and clears nothing — including the orphaned queues it names, whose clearing is a separate
decision. It returns before the branch guard, the lock, the `git add` and the `git commit`, the same
position `checkBranch` occupies and for the same reason: a read must leave nothing half-made.

`blaze commit` stays `mutates: true` — the flush very much mutates. What makes this ONE
invocation runnable under `BLAZE_READONLY=1` (BLZ-121) is `readOnlyFlags: ["--status"]` on the
verb's table entry, an opt-in per-invocation exemption, so every other spelling of the verb is
still refused. Declaring the whole verb read-only would have been the wrong fix, and
that is pinned by a test rather than left to the flag's declaration.

Consequently BLZ-394's blast-radius rule is untouched: the set of files a reconcile commit can name
is still exactly `touched`, and the set a flush stages is still exactly the files recorded against
drained ops. Nothing here widens either, because nothing here commits.

### 5. The last unqualified "sync" claim is removed and pinned

`cli.mjs` described reconcile as `"sync board status to git/PR state"`, rendered to the operator as
`usage: blaze reconcile — sync board status to git/PR state`. It named the whole board, promised a
settled two-way state, and omitted that the verb is dry-run by default — the last surviving instance
of the claim BLZ-404 round 5 removed from every other surface, and pinned by no test. It is replaced
with a bounded description, and a test now pins it so it cannot drift back.

## Consequences

- Reconcile is unchanged. No new flag, field, exit code, probe or failure mode; `scripts/reconcile.mjs`
  is not modified by this decision.
- An operator gains one read-only surface that makes an abandoned queue visible on the day it is
  abandoned, instead of five days later by accident.
- **Cost, accepted:** state (a) remains undecidable after the fact, and `--status` will not surface a
  `per-op` board's failed commit at all, because a `per-op` board keeps no ledger. Both are stated
  in the `--status` report's own trailer rather than left to be discovered.
- **Cost, accepted:** `--status` reports queues belonging to sessions the caller does not own. That is
  deliberate — the 185 orphans span several — and it is a read, never a write, so BLZ-394 is not
  engaged.
- The decision has a scheduled expiry: BLZ-254 retires the git write path in favour of the database,
  at which point the ledger, the flush and this verb are all superseded.

## Alternatives rejected

- **A cross-pass detector in reconcile, in any form.** Rejected on measurement: zero true positives
  over 45 days and 345 commits, against a false-positive state that is the board's normal steady
  state on a `batch` board. This is the fourth rejection of this shape and the first with a figure.
- **A recovery sweep that finishes a previous pass's commit** (BLZ-404 round 2). Rejected already,
  and not narrowed here — nothing in this decision files anything. Its discovery step could not be
  made safe: it named files blaze never wrote, and parsed those names out of porcelain output.
- **A durable failed-commit record**, to make state (a) decidable later. Rejected: it adds a
  persistent artifact, a new failure mode when the record itself cannot be written, and a garbage-
  collection problem, to catch a condition measured at zero and already reported at exit 1 when it
  happens.
- **Having `--status` clear the orphaned queues it finds.** Rejected: a read-only verb that deletes is
  not a read-only verb. `blaze commit --all` already drains them safely; whether stale queues should
  expire on their own is a separate decision on its own ticket.

### 7.2b Deltas from this plan, as actually built

Recorded because the plan is the artifact a reviewer checks the diff against.

1. **`outstandingFiles` needed a third bucket and a second probe.** `git diff --quiet HEAD --
   <path>` alone is **blind to an untracked file**, so a `blaze new` op's brand-new ticket — written,
   queued, never committed — came back `settled`. That is the common case, not an edge one. The
   implementation adds an `existsSync` + `git ls-files --error-unmatch` check ahead of the diff and
   returns `{ outstanding, settled, absent }`. `absent` exists so a path relocated again inside one
   batch (which `commit-runner.mjs` already drops when staging) is not counted as invented work.
   Pinned by **T1b** and by *"a move's old path that is already gone…"*, both added to the plan's ten.
2. **ADR-0030's rule applies to BOTH probes, not just the diff.** T8 was written against the diff and
   caught the gap in the tracked-check: with a stubbed failing `git`, `ls-files` returned non-zero,
   the code read that as "not tracked", and reported an answer it had not earned. Both probes now go
   through one `ask()` helper that admits only 0 or 1 and throws on anything else, `status === null`
   (spawn failed) included.
3. **T6 needed a per-invocation read-only exemption, not a `mutates` change.** `blaze commit` is
   `mutates: true` and must stay so. `cli.mjs` gains `readOnlyFlags: ["--status"]` on that entry and
   an opt-in check beside the BLZ-121 gate, so exactly this invocation is exempt and every other
   spelling of the verb is still refused. Declaring the whole verb read-only would have been the
   wrong fix and would have unblocked a real flush under `BLAZE_READONLY=1`.
4. **T10 lives in `tests/commit-status.test.mjs`, not `tests/commands-doc-quiet-pins.test.mjs`.** That
   file is scoped to reconcile's `--quiet` row, which it reads as its own input; a pin on a different
   page section for a different verb would have been buried there.
5. **T10 grew a second assertion.** It pins the `blaze commit [...]` usage line in `commands.md`

### 7.2c Review round 1 — two blocking defects, both real

PR #158 was refuted on two product-behaviour defects. The design, the measurement, the read-only
property and the bisect point were upheld; these were not.

1. **Over-fire on a symlinked board (blocking).** Covered in ADR §2 above. `--status` reported a
   permanent false `outstanding` for ops that were already filed — the exact 185-orphan condition
   this verb exists to surface, inverted. Reproduced end to end with the real runner, and fixed by
   resolving the recorded path to the path git indexed.

   **T4 was masking it**, and this is the more important half. The original T4 hand-wrote the ledger

2. **The diff probe's ADR-0030 throw was unpinned (blocking).** "All 13 go RED under revert" was

   stub is intercepted by the FIRST probe (`ls-files`), so replacing only the diff probe with a raw

`mutates: false` (it is `mutates: true` + `readOnlyFlags`, and delta 3 above says `mutates: false`

acceptance criterion; and the PR body's coverage figures were wrong.

**Ticketed, not fixed here** (coordinator's call): `--status` crashes with raw stacks on malformed

healthy queues. All crash loudly and none writes, so none is blocking; a status verb should degrade
per-queue instead.

### 7.3 Reachability, stated plainly

- **T8's guard is reachable** — `git` failing to fork or being absent is an ordinary environment

- **`outstandingFiles`'s `absent` branch is reachable** and is the ordinary outcome for a move's old

- **`existsSync && !tracked` is reachable and common** — every `blaze new` op is in that state between
